# SELAH — repository instructions for Codex

## Mission
SELAH is a free, non-commercial Music Ministry Knowledge Center in Bahasa Indonesia, supporting Worship Leaders (WL), singers, musicians, audio and multimedia volunteers. Serve God wholeheartedly, develop skill, and build unity. See PHILOSOPHY.md. The owner approves ministry content and publication.

## Architecture and workflow
- A static, dependency-free PWA hosted on GitHub Pages from `main` / root. No server, database, authentication, build step or Pages CMS by default. Use relative URLs so project sites work under `/repository/`.
- v0.4 navigation: Beranda (`home`), Lagu (`library` + `song/<encoded-id>`), Ibadah (`setlist`, `service`, `arrange`), Belajar (`academy`, `faith`), Lainnya (`more`, `operations`, `reflection`, `manage`, `settings`). Preserve legacy hashes, `selah.v03.state`, `musicMinistry.v1` and schema-1 backup imports. Active storage/backups now use schema 2 for flexible plans. The approved application direction is the owner-supplied Experience Preview; screenshots and verification are in `docs/review/v04/`.
- v0.4.1 interaction: keep functional labels concise and complete reading content in the dedicated modules. Use the shared navigation/action handlers; preserve list state and per-route session scroll, and respect reduced motion. Browser coverage is in `tests/experience-browser.cjs`, `tests/fluidity-browser.cjs` and `tests/welcome-browser.cjs`.
- Read `README.md`, `ROADMAP.md`, and `docs/CONTENT_GUIDE.md` before broad changes. Preserve all modules, the six-song Ibadah Minggu starter and Bahasa Indonesia UI. The v0.5 Service Builder allows editable templates, any number/type/order of segments, multiple locally saved setlists and any song regardless of service category. Worship/Praise filter new song choices by W/P; Bebas (`free`) and other segment types allow both. Preserve existing mismatches and missing IDs on load/import/reconciliation. Confirm before a type change clears incompatible choices; cancelling changes nothing. Group category recommendations separately in the searchable picker. Non-musical segments are optional. Service overrides must never edit master song profiles. Preserve stable segment/entry IDs, both storage keys and schema-1 imports; schema 2 stores the active set, setlists and templates. New copies receive new IDs. Never clear missing or out-of-category song references during migration or reconciliation.
- Published songs live only in `data/songs.json`; use stable IDs, do not overwrite the catalog for a one-song change. `data/legacy-v02.json` is a frozen migration baseline; never edit it for new content. Personal journal, setlist, checklist, progress and song overrides are stored locally, never published by default.
- For song-only requests, modify `data/songs.json`, update `data/version.json` content version, and note changes in `CHANGELOG.md` when useful. Do not update app files or service worker version unless necessary. For app-shell changes, increment app version, displayed version and service worker cache version together. Preserve offline network-first catalog refresh and local overlay semantics. Local edits win per song until user restores public catalog.
- Never put GitHub tokens, credentials, confidential information, personal journal exports, or ministry contact details in the repo. Do not copy user backups wholesale into published files. GitHub Pages is public; attribution/noncommercial status alone does not grant rights. Publish full lyrics only with documented authorization or an applicable lawful basis confirmed by owner. Do not invent lyrics, songwriter/publisher, key, BPM, song form or scripture quotations. Blank unknown fields; thematic biblical references are suggested, not official interpretations. Use user-provided text as supplied within authorized scope. Do not add chord charts unless owner explicitly requests a new scope.
- Brand: Crimson `#E13A26`, Deep Red `#831613`, Baby Yellow `#FEED65`, Canvas `#FCFAF7`, Ink `#30201D`. Use deep red for readable text/action surfaces, yellow sparingly for emphasis, crimson for warmth. No green primary theme. Welcome copy exactly: “Shalom, Hamba Tuhan!”, “Selah, melayani dengan sungguh-sungguh bersama Tuhan.”, “Open”, “Ayat Alkitab”. Keep welcome accessible, mobile-first and functional, with no autoplay sound. Approved visual direction: `docs/welcome-reference.png`; actual responsive UI may differ from illustrative mockup. No automatic publication outside owner's approved workflow.
- Song submissions (v0.5.1): the Add/Edit form exports a single-song `selah-song-submission` schema-1 envelope independently of local saving. Read `docs/CONTENT_GUIDE.md` before applying one. EDIT uses the immutable published baseline captured when the editor opened, not the local override. Preserve its public ID; compare `original` and the observed base content version to the latest catalog before applying only reviewed `changed_fields`. `cleared` is intentional; omitted lyrics/rights must never be cleared. A local-only song is an ADD with no public ID. Neither export nor clipboard publishes or saves. Lyrics and permission text require separate opt-ins; client permission claims are always unverified and need owner review. Never treat a private full backup as a submission. Optional `publishedContentVersion` metadata accompanies `publishedBase` in existing schema-2 storage/backups; do not rename keys or change song/plan schemas for submissions.
- Before a PR run `node tests/validate.mjs`, `node tests/catalog-merge.mjs`, `node tests/service-model.mjs`, `node tests/song-submission.mjs`, `node tests/service-song-picker.mjs`, `node --check assets/song-submission.js`, `node --check assets/app.js`, `node --check sw.js`. For browser changes, follow `docs/ACCEPTANCE_TESTS.md` and report what was actually tested. Do not claim browser/deployment tests if unavailable. Prefer a focused branch/PR and report changed files, content implications, tests and blockers. Do not merge or deploy without owner approval.
